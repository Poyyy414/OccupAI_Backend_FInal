## Findings

### F-01 — One driver can hold multiple active slots

- **Severity:** High
- **Affected area:** Reservation integrity
- **Expected:** A driver should have at most one current `pending_payment`, `reserved`, or `occupied` reservation unless multi-vehicle booking is an explicit product rule.
- **Actual:** PostgreSQL enforces one active claim per `slot_id`, but there is no equivalent active uniqueness rule for `user_id`. Two requests for different slots can both succeed.
- **Probable cause:** `idx_reservations_current_slot` protects the physical slot only.
- **Recommended fix:** Add the intended ownership rule at the database level, normally a partial unique index on `user_id` for current statuses, and convert the resulting unique violation to HTTP 409. If multi-vehicle booking is required, introduce registered vehicle IDs and enforce one active reservation per vehicle instead.
- **Regression tests:** Concurrent same-user/different-slot requests; existing same-slot/two-user race; expiry followed by a new reservation.

### F-02 — Admin manual-payment replay is not idempotent

- **Severity:** High
- **Affected area:** Duplicate payments and duration tracking
- **Expected:** Retrying or double-submitting the same logical payment must return the first result and must not create another payment or duration.
- **Actual:** `/api/payments` does not accept or generate a stable client request key. `_record_parking_payment` supports `external_reference`, but the admin endpoint does not provide one, so a replay can insert a second row.
- **Probable cause:** UI button disabling is being used as the only duplicate-submit protection for manual payments.
- **Recommended fix:** Require a client-generated idempotency key, persist it as `external_reference`, and return the existing row on conflict. Keep the button disabled while the request is pending, but do not rely on UI state for integrity.
- **Regression tests:** Rapid double-click, identical sequential replay, concurrent replay, timeout then retry, and same key with conflicting payload.

### F-03 — GCash checkout can be created without a reservation slot

- **Severity:** Medium
- **Affected area:** Reservation workflow enforcement
- **Expected:** The documented reservation flow requires a specific available slot before advance payment.
- **Actual:** `slot_id` is optional. When absent, checkout creation continues without `_hold_reservation`, producing a parking payment that is not attached to a slot.
- **Probable cause:** The endpoint supports both general parking-plan payment and reservation checkout in one route.
- **Recommended fix:** Separate general plan payment from reservation checkout, or require `slot_id` for the reservation mode and validate the requested operation explicitly.
- **Regression tests:** Missing slot, invalid slot, wrong vehicle type, occupied slot, offline camera, and valid available slot.
